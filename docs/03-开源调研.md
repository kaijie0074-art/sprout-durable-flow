# 开源调研：durable execution / 工作流状态与恢复

> 调研日期 2026-10-13；star 数为当日实测。选型结论：**Temporal 类引擎对这个团队太重（部署+学习成本），务实做法 = SQLite 任务表 + 步骤函数注册表 + 看门狗（源文档 2.3 原话）**——但每一条语义（幂等、检查点、审批门）都从成熟引擎的设计里来。

## 1. Temporal（temporalio/temporal）⭐ 23.6k

https://github.com/temporalio/temporal （Python SDK：[temporalio/sdk-python](https://github.com/temporalio/sdk-python) ⭐ 1.2k）

- **核心思想**：durable execution 事实标准——工作流代码作为"真相源"，引擎持久化每一步事件，崩溃后重放事件历史恢复；Activity 天然要求幂等，自带 retry policy。
- **借用点**：三段式步骤里"执行副作用与确认检查点分离"直接对标 Workflow→Activity→Event History；幂等键的"重放不等于重执行"语义；心跳/超时检测（看门狗）。
- **不采用原因**：需要独立集群（Cassandra/MySQL/ES）+ 学习曲线；单人外包团队的运维成本远超收益（源文档 2.3 已明确论证）。

## 2. DBOS（dbos-inc/dbos-transact-py）⭐ 1.6k

https://github.com/dbos-inc/dbos-transact-py

- **核心思想**：**库形态**的 durable execution——workflow 状态存 Postgres/SQLite，无独立服务；步骤函数标注 `@DBOS.step` 即获幂等与Exactly-once 投递（config-based idempotency）。
- **借用点**：**这是本仓库架构最近的参照**："轻量库 + SQL 存储"路线证明 SQLite 任务表足够撑起 durable 语义；步骤幂等键（workflow+step+key）设计同源。
- **不采用原因**： decorator 依赖其运行时与事务上下文；引入第三方库 vs 自建千行级内聚执行层的权衡中，后者对本业务（审批门/CAS/微信事件耦合）更可控。

## 3. Restate（restatedev/restate）⭐ 4.5k

https://github.com/restatedev/restate

- **核心思想**：durable execution as a service：一次调用一个 durable invocation，带 **idempotent invocation key**（同键调用只执行一次副作用）+ journal 化的 handler。
- **借用点**：幂等键防"客户收到两条消息/商店重复上传"的正是在做的invocation dedup 语义；`waiting_human` 对应其 durable promise/signal（虚拟对象上等一个外部信号，不限时会话）。
- **不采用原因**：自托管仍是独立服务；交互协议偏 RPC。语义被本仓库以 audit 表 + waiting_human 状态实现。

## 4. LangGraph（langchain-ai/langgraph）⭐ 43k

https://github.com/langchain-ai/langgraph

- **核心思想**：Agent 图执行框架，**checkpointer**（thread_id → 状态快照，SQLite/Postgres 后端）让长对话/多步图可恢复。
- **借用点**：检查点=状态快照+恢复游标的建模方式（checkpoints 表）；"图节点即步骤函数"的注册表组织。
- **不采用原因**：定位是 Agent 编排与状态图，不含副作用幂等/审批门/审计；拿它当执行骨架会把业务流水线绑死在 LLM 框架的抽象上（也与"执行层从 Agent 剥离"的架构决策冲突）。

## 5. Celery（celery/celery）⭐ 29k

https://github.com/celery/celery

- **核心思想**：分布式任务队列；`acks_late + task_reject_on_worker_lost` 语义：worker 死亡任务重投——**恰好暴露"重投=副作用重放"的风险**，任务幂等责任在用户。
- **借用点**：反面教材价值：本仓库看门狗的"重入"必须配幂等前置探测才有意义；重投语义上加了 journal has() 探测才敢重跑。
- **不采用原因**：需要 broker（Redis/RabbitMQ）；无审批门/CAS/审计概念。

## 6. LittleHorse（littlehorse-enterprises/littlehorse）⭐ 400

https://github.com/littlehorse-enterprises/littlehorse

- **核心思想**：轻量 workflow 引擎，显式 WfSpec + UserTask（人工任务作为一等公民：任务挂起等人、外部事件唤醒）。
- **借用点**：UserTask → 本仓库 `waiting_human` 状态 + confirm 命令（凭任务 ID，与原会话无关）；external event 关联设计。
- **不采用原因**：仍是独立部署服务；单机 SQLite 对单团队吞吐足够。

## 结论矩阵

| 语义 | 本仓库落点 | 思想源头 |
|---|---|---|
| 断点恢复 | checkpoints 表 + 游标重入 | Temporal event history / LangGraph checkpointer |
| 副作用幂等 | 幂等键 + journal 前置探测 | DBOS step / Restate invocation key |
| 人工等待 | waiting_human + confirm（凭任务 ID） | LittleHorse UserTask / Restate durable promise |
| 高危审批门 | audit APPROVE + waiting_approval | 自建（源文档 2.3），审计留痕参照 Temporal 可观测性 |
| 并发控制 | configs 表 CAS | 乐观并发惯例（etcd/SQLite compare-and-swap） |
| 看门狗 | stale running 重入 + 告警事件 | Celery 重投语义（+幂等才安全）/ Temporal heartbeat |
